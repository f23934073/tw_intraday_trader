# Findings & Decisions

## Requirements
- User initially requested an implementation plan, then explicitly approved execution of Phase 0 / G0 only.
- The intended interpretation is daily-Kbar SMA20/SMA60, consistent with the dashboard labels; retain this as an explicit assumption until the user changes it.
- The plan must keep the existing research-only / no-broker-order boundary.

## Research Findings
- `dashboard/service.py::_moving_averages` computes MA5/20/60 as simple averages of source daily-Kbar closes for the 3-month chart; it has no decision or order path.
- `backtest/strategies.py::EmaCrossoverEntryStrategy` is a distinct EXPERIMENTAL entry: EMA(5) crosses above EMA(20) on completed one-minute Kbars, resets each session, and only evaluates before 12:45.
- `HistoricalBacktestEngine.run` instantiates `BarFeatureState` inside each session loop. The current feature state therefore cannot provide a daily 60-session lookback.
- The basic-strategy-expansion plan already establishes immutable catalog definitions, capability preflight, Decimal calculations, completed-bar-only evaluation, next-bar execution, and experimental default-off semantics. This plan must extend rather than bypass those contracts.
- `_CadenceEvidence` identifies intraday cadence but labels all non-intraday datasets `KBAR_DAILY_TEST_V1` with only `OHLCV`; no `KBAR_DAILY` capability currently exists.
- Provider datasets are sealed as immutable `HistoricalBar` partitions. The dashboard history endpoint is a separate on-demand aggregation path and is not an eligible signal source.
- Application-service strategy preflight is already enforced both before queuing and when executing a run, so a daily capability can be made fail-closed without a new endpoint.
- The engine fills a pending entry only when a later bar has a later timestamp. Therefore a daily-close crossover naturally fills on the next daily bar's open if the daily series is selected.
- There is no ordinary-stock exchange-calendar contract in the current backtest capability layer. The plan must define whether missing trading sessions invalidate the MA window or are explicitly allowed observations; it must not borrow the concurrent TAIFEX premarket calendar work.
- `MarketDataProvider.get_kbars` does not expose a requested bar interval. Mock data returns one daily bar for multi-day requests, whereas the Shioaji mapper treats returned Kbars as raw source bars. A daily strategy must therefore require an explicit, immutable daily-dataset identity rather than infer daily completeness from request length or the dashboard's aggregation.
- `HistoricalDatasetCatalog` already seals provider partitions as immutable bars, so a deterministic daily aggregation/import path can produce a separate dataset without mutating raw source datasets.
- Existing dashboard defaults select all compatible ACTIVE exit strategies. `end_of_day_exit_v1` would close every daily holding at the session close; the plan must make the MA pair experimental/default-off and surface this selection interaction without silently overriding a user's exit choice.
- P0 review confirmed the broad architecture and required four pre-code contracts: explicit daily pending-order horizon, `price_adjustment_policy`, Decimal canonicalization, and resolved session date.
- The current `pending` map is already created before the session loop, so a submitted entry can survive overnight. The P0 issue is nonetheless real: `_evaluate_exit()` treats every `context.is_last_bar` as an `EOD_CLOSE`; because a daily dataset has one bar per session, a death-cross EXIT would otherwise fill on the signal close and violate next-bar timing.
- `context.is_last_bar` means last bar **within the current session**, not last available bar for that symbol in the complete dataset. The revised plan must retain that legacy meaning for `end_of_day_exit_v1` and introduce explicit order horizon / terminal-data semantics for daily strategies.
- `backtest.domain.decimal()` uses `Decimal(str(value))`, while `HistoricalBar.to_dict()` serializes raw `str(Decimal)`. These are good partial protections but do not freeze equivalent-value representation (`103`, `103.0`, `103.00`) in feature/dataset digests.
- `HistoricalBar` has no `session_date`; engine/dataset grouping currently calls `timestamp.date()`. A daily strategy must use a versioned resolver result persisted with the bar/dataset rather than this implicit derivation.
- `DatasetManifest` currently lacks both adjustment and derivation-policy fields; new optional serialized fields must be digest-covered for new manifests while absent legacy fields preserve existing manifest digests.
- G0 scope is limited to source qualification artifacts: raw Provider payload shape, timestamp/numeric representation, resolved session date, completion evidence, chunk boundaries, and a deterministic qualification result. It must not implement SMA, strategy registration, Dashboard changes, or broker execution.
- This checkout is already materially dirty from concurrent work (28 tracked files plus untracked packages/plans). Existing `backtest` and Provider changes are external baseline; G0 must use new isolated qualification files or avoid overlapping edits.
- `market_data/capture_artifacts.py` and `market_data/quote_qualification.py` establish a useful offline, fail-closed artifact pattern: schema-versioned JSON, byte/digest checks, explicit issues, and `INCOMPLETE` when required evidence is absent. The new Kbar qualification must be a separate schema rather than extending quote-parity artifacts.
- `ShioajiProvider.get_kbars()` exposes no resolution argument and maps raw Kbar values into application `KBar` values. G0 therefore needs an SDK-facing capture boundary which preserves each raw field's type and textual representation before normal mapping; testing only mapped provider results cannot establish the source numeric contract.
- Existing `research/captures/quote_parity/` samples contain quote-stream events rather than Kbar rows. They cannot establish daily cadence or session completion and must not be relabelled as G0 evidence.
- G0 live capture on 2026-08-19 (Shioaji SDK 1.7.2, symbol 2330) produced 266 raw Kbars for 2026-08-18. The raw values were `int` timestamps and volumes but `float` OHLC values; the timestamp resolved under the current Provider wall-time convention to 09:01–13:30 Asia/Taipei. It is therefore an intraday source, not an explicit daily source.
- A current-session capture at 12:16 Asia/Taipei contained 197 rows from 09:01 to 12:17 and was correctly labelled incomplete. Its final timestamp is later than local capture time, so `TIMESTAMP_AFTER_CAPTURE_TIME` preserves the unresolved bar-label/clock semantic rather than assuming a bar-start meaning. Three independently queried 2026-08-18 captures had the same raw-row digest, and an adjacent 2026-08-17/18 chunk comparison had no duplicate resolved session dates.
- The official TWSE 2026 holiday CSV was retrieved and recorded as a calendar contract with raw-byte SHA-256 `2127b6c20ea3dbdb47763b99115b445a49994faffe54de9d5cd9bfa70c2b4f0b`; the raw fixture and qualification reports can be replayed offline.
- The source response exposes neither a finalization marker nor a completion watermark. Time coverage plus repeat-digest evidence is insufficient to claim source completion, so the selected path is correctly `BLOCKED`, with `DERIVED_FINALIZED_SESSION_V1` only a future candidate if finalization evidence is added. `SOURCE_FLOAT_LOSSY` remains the planned P1 issue and does not get silently normalized away.
- Phase 8 candidate evidence is TWSE's public monthly `STOCK_DAY` daily report. The 2026-08-18 row for 2330 provides official daily volume, open, high, low, and close, and TWSE regulations state that these fields are published in a daily securities market report after market closing. The endpoint itself notes that its daily aggregate includes regular, odd-lot, after-hours fixed-price, and block transactions, so volume equality with Shioaji's regular-session Kbars must be measured rather than assumed.
- Measurement confirms the scope issue: the captured Shioaji 2026-08-18 aggregation is OHLC-equal to the official row (`2415/2415/2375/2380`) but its raw Volume sum is `17,217`, while the TWSE daily report is `19,997,213` shares. The magnitude strongly suggests lots-versus-shares plus different session coverage, but neither conversion factor nor scope is proven by the current capture. Phase 8 must preserve this mismatch as a separate volume contract issue; it cannot claim full OHLCV equality.
- Shioaji's official historical-Kbar documentation establishes `ts` as Unix timestamp, OHLC as `float`, and `Volume` as integer volume; its own stock example also contains `Amount`. Phase 8 will use a new local capture including `Amount`, rather than relying only on documentation, to prove whether a 1,000-share common-lot multiplier explains the captured values.
- Phase 8 live evidence completed: a new 2026-08-18 raw Shioaji capture included `Amount`; all 266 nonzero bars satisfied `low <= Amount / (Volume * 1000) <= high`. This proves `Volume` is a 1,000-share common-lot unit for this captured stock/session, not merely an inferred daily-scale conversion.
- The independently captured raw TWSE `STOCK_DAY` response has the same session date and exactly matches Shioaji regular-session open/high/low/close (`2415/2415/2375/2380`). It is a replayable end-of-session completion proof. The TWSE total volume/amount do not equal Shioaji's 09:01–13:30 aggregate, as expected from the official report's broader scope; the selected source contract therefore records `SHIOAJI_REGULAR_SESSION_COMMON_LOTS_V1` rather than falsely presenting it as the official all-session daily total.
- G0 now selects `DERIVED_FINALIZED_SESSION_V1` with no operational blockers. `SOURCE_FLOAT_LOSSY` remains P1 and `RAW_CORPORATE_ACTION_UNADJUSTED` remains a formal-research blocker only; neither was hidden or reclassified as a pass.
- Phase 9 current-code reconciliation: the concurrent basic-strategy expansion has already introduced `backtest-engine-v2`, session-local `BarFeatureState`, experimental intraday strategy definitions, capability preflight, and a pending map that survives session loops. It has not implemented daily features, daily capability, resolved session metadata, or execution horizons. The daily slice must be additive and avoid changing those existing intraday semantics.
- The current engine groups on `bar.timestamp.date()` and fills every exit at session close when `context.is_last_bar`; both must be extended carefully for the daily family. The existing `TradeDecision` and `_PendingOrder` have no horizon, and the provider historical mapper converts raw source values to `float`, so daily ingestion must remain a new explicit path rather than reuse generic provider download output as evidence.
- `DatasetManifest` currently has legacy-digest compatibility support via optional cadence serialization, and `HistoricalBar.to_dict()` is the checksum payload. Daily metadata and `session_date` therefore must be optional-and-omitted for legacy objects, while mandatory for the new derived path. The new derivation will require a per `(symbol, resolved_session_date)` completion-proof digest; a single G0 sample cannot silently qualify an arbitrary multi-year provider dataset.
- Implemented the Phase 9 data boundary: optional/legacy-omitted `HistoricalBar.session_date`, digest-covered daily manifest metadata, and a full-materialized `create_derived_daily_dataset()` path. It requires an intraday parent, a versioned session contract, `RAW` policy, `REGULAR_SESSION`/`COMMON_LOT` volume contract, and completion-proof digest for every source symbol-session. The derived child is explicitly `KBAR_DAILY_V1`, `DERIVED_FINALIZED_SESSION_V1`, and research-ineligible; parent bytes are unchanged.
- Existing strategy expansion tests establish strict legacy engine reproducibility, so horizon fields need additive defaults matching existing `NEXT_BAR_OPEN` behaviour. The new daily feature state can stay separate from `BarFeatureState`; `simple_moving_average` belongs in `backtest.indicators` and daily strategy context should be optional so ordinary strategies do not observe a changed contract.
- The dashboard strategy selector is already capability-aware and defaults only `ACTIVE` definitions, so the two SMA definitions remain default-off without a special case. It needs only a non-blocking warning when a user explicitly combines either SMA strategy with `end_of_day_exit_v1`.
- A daily derivation CLI needs a reviewable proof-bundle input rather than a date range or a generic G0 result: a single G0 reconciliation proves only its captured `(symbol, session)` and must not implicitly authorize every parent session.
- Phase 9 verification passed for every SMA-related unit, catalog, service/worker, UI, and legacy-backtest regression test (35 tests). The complete suite reached 383 passed and 1 skipped before a separate premarket test rejected an already-existing, untracked immutable artifact with the same digest but different bytes. That artifact was not altered; it is outside the daily SMA scope.

## Technical Decisions
| Decision | Rationale |
|----------|-----------|
| Daily SMA crossover is a new `ENTRY` strategy | It is semantically different from EMA(5/20) and requires different cadence/state semantics. |
| Do not source signal inputs from the dashboard history route | That route makes on-demand Provider requests for charting; historical strategy inputs must remain an immutable selected dataset. |
| Use an isolated daily feature state rather than extending session-local `BarFeatureState` | ORB/EMA/RSI/ATR semantics intentionally reset per session; conflating them would create regression risk. |
| Treat calendar completeness as an explicit prerequisite for formal research qualification | A rolling 60-observation SMA can execute under the initial capability, but missing sessions must be visible and cannot silently be treated as a complete market calendar. |
| Use a sealed daily dataset with explicit derivation metadata | A request range or one bar per observed date alone cannot prove that a source bar is a finalized daily bar. |
| Implement both golden-cross entry and death-cross exit as independently selectable experimental strategies | The user asked for crossover signals; the two directions have different `ENTRY`/`EXIT` roles and must not be forced into one aggregation rule. |
| Add `price_adjustment_policy: RAW` in v1 | It freezes the price sequence's semantics without falsely claiming corporate-action adjustment or formal research eligibility. |
| Canonicalize decimal values before every strategy/dataset feature digest | Equivalent numeric inputs must produce identical evidence hashes; binary float payloads are rejected at the source boundary. |
| Resolve and persist `session_date` through a versioned session contract | Daily aggregation must group by an official resolved session rather than blindly use timestamp calendar date. |

## Issues Encountered
| Issue | Resolution |
|-------|------------|
| The first daily next-bar integration fixture left its position unresolved | `symbol_event_indexes` resets each session, so the existing first-bar exit guard suppressed the only completed daily close after an overnight daily entry. Preserve the guard for intraday fills, but allow a `DAILY_NEXT_BAR_OPEN` position to evaluate the completed close of its fill session. |
